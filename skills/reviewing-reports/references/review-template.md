# 原生批注与交付规范

## 结构化问题清单

问题清单仅作临时输入，不是交付物。JSON 顶层必须为 `files` 数组；每个待审核文件必须出现一次，零问题时 `issues` 为空数组。

```json
{
  "files": [
    {
      "file_id": "f001",
      "issues": [
        {
          "issue_id": "f001-i001",
          "kind": "point",
          "severity": "较大",
          "location": "表4-2，第3行，夜间叠加值",
          "original_kind": "value",
          "original": "50.0 dB(A)",
          "reason": "背景值为48.0 dB(A)、贡献值为49.0 dB(A)，按能量叠加公式计算为51.6 dB(A)",
          "correct": "51.6 dB(A)，保留1位小数",
          "action": "直接将本单元格的50.0改为51.6",
          "table_id": "表4-2",
          "row_label": "第3行",
          "anchor": {
            "format": "xlsx",
            "sheet": "噪声预测",
            "cell": "G6"
          }
        }
      ]
    }
  ]
}
```

必填字段：`file_id`、`issue_id`、`kind`、`severity`、`location`、`original_kind`、`original`、`reason`、`correct`、`action`、`anchor`。严重度仅允许“重大/较大/一般/文字”；`original_kind` 仅允许 `value/text`；`kind` 仅允许 `point/table_summary/section_summary`。

同一章节内多个同类缺项共用一个原因和闭合动作时，可用 `section_summary`，并填写非空 `section_id` 和去重后的 `affected_items`。例如附件目录系统性缺件可锚定“8.2附件”，逐项列出实际缺失且影响结论的附件；不得拆成重复批注，也不得借汇总类型写“全文检查”。

DOCX 锚点使用 `format=docx`、稳定 `paragraph_path` 和非空 `anchor_text`；脚本优先选择包含该文字的最小唯一 run，无法唯一命中时退到该非空段落。XLSX 锚点使用 `format=xlsx`、`sheet` 和 `cell`。

## 批注拼装

脚本固定拼装：

> 【严重度｜精确位置】原值/原文“X”；原因及依据。正确值/判断应为Z。修改动作：……

每条必须同时具备：精确位置、准确原值/原文、错误原因、正确结果或闭合分支、直接修改动作。不得让编制人员自行发现问题。

## 数值表与公式

- 每个错误单元格分别建一条 `point` 问题，写明对象、字段、原值、代入式、结果、单位和精度。
- `table_summary` 仅在一条汇总批注能明显减少阅读成本时选用，不因同表出现多条数值 `point` 而强制创建。若创建，`affected_rows` 必须列全所有 `row_label`，修改动作必须写“只修改上述所列行，未列行无需复核”。
- 噪声叠加使用 `L总=10lg(10^(L背景/10)+10^(L贡献/10))`。先用未取舍值计算，再按目标表小数位取舍；表内无一致精度时保留1位小数。
- 无法唯一确定正确值时，不得要求全表重算。只指定一个必要原始字段或一行记录，并列出所有闭合分支。

闭合分支格式：

> 仅查看本行夜间贡献值：若为A，则叠加值改为B；若为C，则贡献值改为D、叠加值改为E。其余行无需复核。

## 单位字形

- 批注全文中的面积、体积单位统一使用真实角标，如 `m²`、`m³`、`hm²`、`dm³`、`km²`；不得写成 `m2`、`m3`、`hm2`、`dm3`、`km2` 或 `m^2/m^3`。
- 引用原值或原文时，允许仅将伪角标规范为真实角标，但数值、正负号、小数位和语义必须保持不变；锚点文字仍按报告原文填写。
- 合法变量、标准号或路径中的 `m2/m3` 不作单位改写；问题字段应明确写出“变量/标准号/路径”语境，变量也可用反引号标识，避免与单位混淆。
- 守护脚本在生成批注时自动规范明确的面积、体积单位，并在 OfficeCLI 回读后检查原始字形。不得用 NFKC 等兼容性规范化结果判断角标正确，因为该规范化会把 `²/³` 折叠为 `2/3`。

## 禁用泛化措辞

批注的原因、正确结果和修改动作命中下列表述即拒绝写入；`original` 可忠实引用原报告中的相同文字：

- `请核对`、`请复核`、`请核实`、`请确认`。
- `建议核对`、`建议复核`、`建议核实`、`建议确认`、`建议完善`。
- `需核对`、`需复核`、`需核实`、`需确认`、`需进一步核实`。
- `逐项重算`、`全面检查`、`全面复核`、`可能有误`、`自行确认`、`确认后修改`、`核实后修改`。

## 去重与跨文件问题

- 同一文件内的新批注规范化全文不得重复，也不得与该文件原有批注全文重复；不同文件可出现相同批注。
- 权威值明确时只批注错误文件；无法确定时按 `evidence-and-crosscheck.md` 在两处写成对批注。
- 同一事实被多个章节引用时，优先批注源头错误，并在修改动作中列出必须同步修改的明确位置；不得写“全文统一”。

## 最终交付汇总

最终回复保持简短，依次报告：

1. 审核结论；命中重大退回条件时写“建议退回修改后复核”。
2. 审查限制及最小补充材料。
3. 每个文件的新增批注总数、重大/较大/一般/文字分布及输出绝对路径。
4. 1至5项关键问题，不另附完整问题清单。
5. 按验收档位报告原件哈希、输出数、批注回读、锚点、重复、禁词、正文快照和压缩包结果；跳过项明确标记 `not_performed_by_profile`，视觉检查始终标记 `not_performed_by_design`。
6. 权威联网来源及访问日期。
7. 精简清单优化建议；无新增经验时写“本次未发现需要更新审核清单的事项”。

不得把内部 JSON、工具日志、推理过程或聊天内容放入成果文件。成功发布后清理临时状态和问题清单。
