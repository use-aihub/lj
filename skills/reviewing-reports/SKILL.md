# 专业报告原生批注审核

## 交付原则

- 直接读取和处理 `.docx`、`.xlsx`，不得为审核做无意义格式转换。
- 原件绝对不写入。先锁定待审核清单、SHA-256 和原有批注，再在临时区复制、写入和验收。
- DOCX 使用 Word 原生批注及非空文字锚点；XLSX 使用目标单元格经典批注/备注。作者固定为“审核助手”。
- 同一项目内全部目标通过后发布；多个独立项目分别建状态、分别发布，任一项目失败不得阻塞其他项目。默认输出到原件同目录，名称依次为 `原文件名-审核批注版`、`-v2`、`-v3`。
- 不强行凑问题。零问题文件仍发布零新增批注副本，保证输出数等于待审核数。
- PDF、图片、扫描件及其他附件只在影响重大结论时读取必要内容，不生成对应批注版。
- 用户明确要求“只审不改”或“先给预览”时，保持只读，并明确未执行文件交付验收。
- 任何验收档位均不得渲染 DOCX/XLSX，不生成 PDF、PNG 或页面截图做视觉检查。

## 先读资源

- 输变电环评、电磁、噪声、生态类材料：读取 `references/transmission-ai-review-checklist.md`。
- 水土保持设施验收材料：读取 `references/water-conservation-acceptance-checklist.md`；不加载与任务无关的输变电环评专项判断。
- 所有多文件或涉及附件、附图、外部证据引用的任务：读取 `references/evidence-and-crosscheck.md`。
- 写问题清单和批注前：读取 `references/review-template.md`。
- 判断严重程度和退回结论前：读取 `references/return-criteria.md`。
- DOCX/XLSX 操作：遵循 OfficeCLI 的 `word` 或 `excel` 格式技能；命令不确定时先运行 `officecli help`。

## 工作流

1. 清点材料，区分正文、专题、批复、可研/设计、监测报告、原始记录、附图及一般附件。排除临时文件和既有“审核批注版”。
2. 明确待审核 DOCX/XLSX。用户只给文件夹且目标边界不明时，在任何写入前只确认一次目标清单。多个独立项目按可用并发槽分派，一个项目只由一个代理持有状态和写入权；项目完成即交付，不等待全批。
3. 使用 `scripts/review_artifact_guard.py prepare --profile fast` 快速预检。失败只停止当前项目，不影响其他项目。
4. 用 OfficeCLI L1 读取标题、正文、表格、公式、批注和结构。长报告先完成一次保留对象路径的全文抽取，再定点回读候选段落和表格，避免反复全文读取。内部建立工程事实底表，不把完整底表作为交付物。
5. 逐文件深审，再按事实底表交叉核对。只记录有证据、可定位、可执行的问题。
6. 按 `review-template.md` 形成结构化 JSON 问题清单并去重。每条填写位置、原值/原文、原因、正确结果或闭合分支、修改动作和锚点。
7. 使用守护脚本 `write` 按文件一次性预检全部锚点，再用一次原子批处理写入全部批注。同一文件只允许一个写入者；不得直接修改正文、表格、公式或格式。
8. 使用守护脚本 `verify --publish` 按状态中的验收档位复核并立即发布当前项目。任一项失败不得发布该项目。
9. 用简体中文给出简短交付汇总，不另做问题清单代替文件批注。

跨平台调用：macOS/Linux 使用 `python3`，Windows 使用 `py -3`。

```text
python3 scripts/review_artifact_guard.py prepare --profile fast --state <state.json> --input <file1> --input <file2>
python3 scripts/review_artifact_guard.py write --state <state.json> --issues <issues.json>
python3 scripts/review_artifact_guard.py verify --state <state.json> --issues <issues.json> --publish
python3 scripts/review_artifact_guard.py cleanup --state <state.json>
```

`<state.json>` 和 `<issues.json>` 必须放在本次任务临时目录，不得放入原件目录。

| 子命令 | 职责 |
|---|---|
| `prepare` | 锁定项目目标，按档位记录 SHA-256、原有批注和所需快照；默认 `fast` |
| `write` | 在一次性副本批量预检锚点，从不可变基线重建，再按文件原子批量写批注 |
| `verify --publish` | 按档位验收当前项目；通过后立即发布并清理临时副本、状态和问题 JSON |
| `cleanup` | 清理失败任务的临时副本及状态，不触碰原件和既有正式输出 |

## 验收档位

| 档位 | 检查内容 |
|---|---|
| `fast`（默认） | 原件 SHA、原批注、正文快照、批注及锚点回读、ZIP 完整性 |
| `balanced` | `fast` 全部内容，加 outline 结构快照 |
| `strict` | `balanced` 全部内容，加 annotated、OfficeCLI validate、真实页数及可用时的 `unzip -tq` |

只在用户明确要求全面验收或项目风险较高时使用 `strict`。`write` 和 `verify` 自动继承 `prepare` 档位，不得中途切换。所有档位的 `visual_review` 均为 `not_performed_by_design`。

## 工程事实底表

按任务类型抽取事实。输变电材料至少包括项目名称、建设单位、项目代码、核准文号、电压等级、工程组成、主变数量及容量、线路起终点和长度、杆塔、导地线、额定电流、最低线高、评价范围、敏感目标、监测点、标准、预测参数、环保措施和结论；水保验收材料至少包括许可与建设时序、防治责任范围、占地、土石方、表土、措施工程量、投资、单元工程、六项指标、监测/监理、附件和验收结论。记录每个值的文件、章节、表号或对象，禁止只存孤立数值。

通用技术报告仅审事实、计算、抄录、引用、证据和跨文件一致性，不套用输变电专用判断。

## OfficeCLI 纪律

- 严格遵循 L1 读取 -> L2 原生编辑 -> L3 原始 XML。L2 已支持批注时不得绕到 L3 写 XML。
- 所有写入和回读子进程设置 `OFFICECLI_NO_AUTO_RESIDENT=1`；批处理一次完成打开、操作和保存，不额外调用 `close`。
- 原件和不可变基线不得传给 OfficeCLI。`batch get` 仅针对一次性预检副本；正式 stage 必须在预检后重新从基线复制。
- 同一文件的全部批注使用一次默认原子模式的 `officecli batch --stop-on-error` 写入，禁止逐条启动 OfficeCLI。
- `validate`、`batch` 及其他可能重封装文件的命令仅处理临时副本。
- 不得调用任何渲染、页面截图或视觉验收工具；不以视觉检查作为发布条件。
- DOCX 真实页数仅在 `strict` 且 OfficeCLI 可取得时比较；首次不可用后跳过本任务其余文件，不得用结构节点数代替页数。

## 联网核验

仅当法规、标准版本、地理保护目标、资质或外部事实会改变结论时联网。只采用政府、标准发布机构或其他权威一手来源。批注写明发布机关、文件/标准号及条款；最终汇总集中列 URL 和访问日期。无法证实时不得编造，也不得用“可能有误”代替证据。

## 交付口径

写入任务的最终回复必须包含：审核结论、审查限制、每个文件的新增批注数及严重程度分布、关键问题、输出绝对路径、权威联网来源、各项验收结果和精简清单优化建议。只读或预览任务仅报告结论、限制、关键问题、最小补充材料和来源，并明确“未写入文件，未执行交付验收”；不得虚构输出路径、批注数或验收结果。

命中重大退回条件时明确写“建议退回修改后复核”。材料不足时写“审查受限”，仅列最小补充材料。不得擅自修改本技能或审核清单；只有用户明确要求更新技能时才修改。
